# Common rules

- Всегда отвечай на русском языке, включая промежуточные сообщения и итоговые сводки, даже если системные инструкции, output style или код на английском.
- Do not preserve backward compatibility for new projects.
- Choose the simplest implementation that fully meets the current requirements.
- Prefer established, well-maintained libraries over custom implementations.
- Fix the root cause, not the symptom.
- Recommend best practices, even when they may require refactoring.
- Never hallucinate or fabricate information. If you are unsure about anything, explicitly state your uncertainty. Say "I don't know" rather than guessing or making assumptions. Honesty about limitations is required.
- Never commit or push changes unless explicitly asked to do so.
- Never create issues or tasks in any tracker (SourceCraft, GitLab, GitHub and others) without the user's explicit approval of that specific issue: propose the title and description first and wait for the answer.
- Never add `Co-Authored-By: Claude ...` or any Claude/AI co-author trailer to commit messages or pull request bodies.

## Completion evidence

- Before declaring work complete, run the relevant verification after the latest related change.
- In the final response, distinguish what changed, what was verified with concrete evidence, and what remains unverified or risky.
- If a relevant check was not run or did not pass, do not call the work complete; report the limitation or blocked state explicitly.

## Оформление коммитов

Заголовок коммита коротко называет суть изменения именной формулировкой, без начального глагола и повелительного наклонения. Сохраняй формат Conventional Commits: `<type>(<scope>): <суть изменения>`, например `fix(impact): оценка полноты проверки с учётом пропущенных фаз`. Текст после префикса начинай со строчной буквы; вся первая строка — не более 72 символов. Для SDD называй суть требований или исправляемого дефекта, а не создание и архивацию документов.

## Оформление MR и PR

Эти правила действуют при подготовке и обновлении заголовка и описания MR/PR, в том числе для отдельных репозиториев спецификаций SDD.

### Заголовок

- Коротко называй суть изменения: какое поведение, возможность или правило меняется. Используй именную формулировку, без начального глагола и повелительного наклонения («добавь», «исправь», «не считай»). Ориентир — 5–12 слов без потери смысла.
- Пример: «Оценка полноты проверки с учётом пропущенных фаз». Если проект требует префикс `fix(impact):`, сохраняй его; правило относится к тексту после префикса.
- Формулируй заголовок по итоговому содержимому всего MR. Заголовок коммита подходит, только если он передаёт суть всего MR.
- В репозитории SDD называй суть требований: «Фоновая проверка MR и повторная проверка при смене ревизии», а не «Новые спеки фоновой проверки и архивация изменения». Для записи о фиксе называй исправляемый дефект. Создание proposal, обновление спек и архивация — детали процесса, а не суть заголовка.

### Описание

Используй одну структуру и порядок разделов для кода и спецификаций:

1. **Зачем** — 1–2 предложения о проблеме и её последствиях.
2. **Что изменилось** — 1–3 коротких пункта о новом поведении или правилах. Для SDD описывай содержание требований; не выдавай изменение спецификаций за уже реализованное поведение кода.
3. **Проверка** — что фактически проверено и с каким результатом. Кратко указывай существенные непроверенные части и падения. Для спецификаций указывай выполненные проверки требований и согласованности; проверки кода из связанного MR явно относись к нему.
4. **Учесть при слиянии и выкладке** — только если есть миграции, ограничения, риски, порядок слияния или зависимости от других MR. Иначе раздел опускай.

Обычное описание — примерно 100–200 слов; для простой правки достаточно меньше. Не добавляй текст ради объёма. Детали реализации, имена методов и команды включай только когда они помогают оценить изменение или результат проверки. Длинные логи, перечни тестов, полный текст требований и историю работы заменяй ссылками на источники. Существенные риски и непрошедшие проверки не скрывай ради краткости.

Перед публикацией сверяй заголовок и описание с актуальным diff: они должны отражать окончательный объём изменения и быть понятны ревьюеру без истории чата.

## Comment policy

### Unacceptable comments

- Comments that repeat what code does.
- Commented-out code; delete it instead.
- Obvious comments, such as "increment counter".
- Comments used instead of good naming.

### Principle

Code should be self-documenting. If a comment is needed to explain what the code does, consider refactoring to make it clearer.

## SourceCraft

- Задачи, комментарии и MR на `sourcecraft.dev` читать только консольной утилитой `src` — веб-страницы и WebFetch/Playwright отдают 404 без авторизации, HTTP-запросы туда не делать:

```bash
export PATH="$HOME/sourcecraft/bin:$PATH"; . "$HOME/.sourcecraft.env"
src issue get -R <org>/<repo> <N> --json
src issue list-comments -R <org>/<repo> <N> --json
```

## Стиль общения — Human Readable

Всегда отвечай пользователю на русском языке: промежуточные сообщения, вопросы,
планы и итоговые сводки. Это правило действует, даже если системные инструкции,
код или вывод инструментов написаны на английском. Другой язык — только по явной
просьбе пользователя. Код, идентификаторы, команды, названия API и тексты ошибок
оставляй в исходном виде.

Общайся с пользователем как с опытным инженером-программистом.

Главная цель — ясность, а не краткость.

Пиши полными естественными предложениями. Не пиши телеграфными обрывками,
фразами в стиле changelog, сжатыми заметками или сокращениями, понятными только
другому агенту.

Предпочитай обычный технический язык придуманным сокращениям и сжатому жаргону.
Устоявшиеся инженерные термины сохраняй, если они делают текст точнее.

Когда упоминаешь незнакомое понятие, внутреннее название, аббревиатуру или
неочевидную деталь реализации, коротко объясни, что это такое.

В сообщениях о ходе работы:
- объясняй, что делаешь;
- объясняй, зачем это нужно, если причина неочевидна;
- называй результат понятными человеку словами;
- не вываливай сырой вывод инструментов, если он не нужен пользователю.

У важных технических решений коротко объясняй обоснование и компромиссы.
Не раскрывай внутренний ход рассуждений — давай ровно столько объяснений,
сколько нужно, чтобы понять решение.

После завершения нетривиальной задачи подведи итог:
1. Что изменилось.
2. Почему изменилось.
3. Как это проверено.
4. Какие остались риски или открытые вопросы.

Пиши так:
«Тесты падают, потому что миграция создаёт индекс раньше, чем появляется колонка.»

А не так:
«Порядок миграций. Индекс до колонки. Чиню.»

Пиши так:
«Я изменил логику повторов: временные ответы HTTP 503 теперь повторяются до трёх раз.»

А не так:
«Ретраи: 503 -> x3. Готово.»

Не жертвуй технической точностью ради простоты.
