# GitLab MR Review

Работай как независимый reviewer, а не автор изменения. По умолчанию только исследуй и сообщай
результат: не правь код, не коммить, не push'и и не меняй состояние MR.

## Обязательные правила

- Сначала прочитай действующие `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` и локальные инструкции
  затронутых каталогов. Правила репозитория имеют приоритет над этим общим workflow.
- Не переключай рабочее дерево на ветку MR поверх пользовательских изменений. Исследуй точные SHA
  через `git show`/`git diff`; для запуска веточного кода используй изолированный временный каталог.
- Не исправляй найденное: запрос на ревью разрешает диагностику, но не реализацию.
- Не публикуй комментарии, approve, resolve, labels или изменение статуса MR без явного запроса.
- Не считай замечание верным только из-за severity или мнения прежнего reviewer. Проверяй его на
  текущем коде, поддерживаемом сценарии и фактическом влиянии.
- Не печатай токены и URL с embedded credentials. Не выводи proxy-переменные.

## 1. Зафиксировать состояние MR

1. Из URL или запроса определить host, namespace/project и IID.
2. Проверить локальный контекст: `git status --short --branch`, текущую ветку и безопасный remote.
3. Через `glab mr view <iid> -R <namespace/project> -F json` получить как минимум:
   - `source_branch`, `target_branch`, `sha`;
   - `diff_refs.base_sha`, `start_sha`, `head_sha`;
   - состояние MR, конфликты, draft, approvals и pipeline;
   - описание, автора и число notes.
4. Прочитать существующие discussions и статусы commit/pipeline через GitLab API. Зелёный pipeline —
   свидетельство, но не доказательство, что новые тесты действительно подключены и покрывают риск.
5. Fetch source и target refs без checkout. Проверять именно диапазон `base_sha..head_sha`; отдельно
   посмотреть список коммитов, `--stat`, `--name-status` и `git diff --check`.

Если пользователь требует работу без proxy, каждый сетевой вызов выполнять локально очищенным
окружением, не изменяя shell глобально:

```sh
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
    -u http_proxy -u https_proxy -u all_proxy \
    glab <command>
```

Если такого требования нет, сохранять текущую сетевую конфигурацию; при сетевой ошибке не делать
вывод о состоянии MR до успешного повторного чтения.

## 2. Построить карту риска

Сгруппировать изменённые файлы по назначению: runtime-код, API/контракты, миграции, auth/security,
конкурентность и транзакции, конфигурация/deploy, prompts/skills, тесты и документация. Для каждой
группы прочитать не только diff, но и ближайших callers/consumers, действующие спецификации и тесты.

Составить короткий план проверок по реальным границам изменения. Если правила репозитория требуют
субагента и проверки независимы, делегировать ограниченную ось, а критичность и итог перепроверить
основным агентом.

## 3. Проверить и воспроизвести

Проверять прежде всего:

- корректность happy path, ошибок, пустых/граничных значений и повторных вызовов;
- обратную совместимость API, persisted data, конфигов и runtime-образов;
- авторизацию, валидацию ввода, утечки секретов и расширение полномочий;
- race conditions, идемпотентность, транзакционные границы и восстановление после сбоя;
- миграции вперёд/назад, порядок rollout и смешанные версии компонентов;
- соответствие тестов изменённому поведению, включая отрицательные сценарии;
- ложные успехи/ошибки validator'ов, prompts и автоматических гейтов.

Запускать проверки пропорционально риску. Веточный код, которого нет в рабочем дереве, извлекать в
изолированный временный каталог или запускать из отдельного контейнера; не загрязнять пользовательскую
ветку. Явно отделять успешно выполненные проверки от тех, которые не удалось запустить.

Каждый кандидат в finding обязан иметь все четыре свойства:

1. замечание относится к изменённой строке или является прямым следствием изменения;
2. сценарий поддерживается текущими требованиями/runtime, а не является теоретическим legacy-case;
3. дефект воспроизводим кодом, тестом или строгой трассировкой исполнения;
4. влияние на пользователя, данные, безопасность, поставку или достоверность гейта конкретно названо.

Не выносить finding, если это только стиль, уже проверяемый formatter/linter; неизменённый baseline
debt без новой регрессии; предположение без воспроизведения; либо возможность вне согласованного scope.
Такие подозрения при необходимости перечислить как проверенные и отклонённые.

## 4. Назначить severity и оформить findings

Если репозиторий задаёт свою шкалу, использовать её. Иначе:

- `P0` — немедленная потеря данных, компрометация или массовая недоступность без безопасного обхода;
- `P1` — blocker поддерживаемого сценария, поставки, безопасности или целостности данных;
- `P2` — существенный дефект с ограниченным сценарием/обходом либо достоверная ложная работа гейта;
- `P3` — небольшая, но реальная проблема, не сводящаяся к вкусу.

Не завышать severity из-за размера diff или формальной важности файла. Формат одного finding:

```markdown
[P1] Короткий заголовок по наблюдаемому дефекту

`path/to/file:line`

Условие воспроизведения → фактическое поведение → ожидаемое поведение и влияние.
Кратко указать направление исправления, не проектируя за автора полный patch.
```

Сортировать findings по убыванию severity. Несколько проявлений одной причины объединять; независимые
причины не смешивать в один комментарий.

## 5. Вернуть результат пользователю

Начать с рекомендуемого вердикта: `Request changes`, `Comment` или `Approve`. Затем перечислить
findings с точными файлами/строками и доказательствами. После них кратко указать:

- состояние pipeline и реально выполненные локальные проверки;
- что не удалось проверить и какой residual risk остался;
- проверенные, но отклонённые подозрения, если они помогают понять scope;
- что рабочее дерево и MR не изменялись.

Если доказуемых findings нет, прямо написать «замечаний нет», не придумывая их ради формального ревью.

## 6. Опубликовать замечания только по запросу

Перед публикацией повторно прочитать discussions и актуальный `head_sha`, чтобы не создать дубликаты
и не привязать комментарии к устаревшему diff.

- Публиковать каждый независимый finding отдельным resolvable discussion.
- Предпочитать inline-комментарий на изменённой строке. Для добавленной строки использовать
  `new_path`/`new_line`, для удалённой — `old_path`/`old_line`.
- Передавать position как вложенный JSON-объект с точными `base_sha`, `start_sha`, `head_sha` через
  Discussions API; не полагаться на form-поля с буквальными ключами `position[...]`.
- Если строка не входит в diff, создать общий discussion и явно написать `path:line` в теле.
- После отправки прочитать discussion обратно и проверить тип diff-note и сохранённую position.
  `resolvable=true` само по себе не доказывает inline-привязку.
- При force-push заново получить diff refs и перенести line position до повторной отправки.
- Не approve'ить MR и не resolve'ить чужие threads, если пользователь не попросил об этом отдельно.

JSON position для inline-discussion имеет форму:

```json
{
  "body": "[P1] ...",
  "position": {
    "position_type": "text",
    "base_sha": "<base_sha>",
    "start_sha": "<start_sha>",
    "head_sha": "<head_sha>",
    "new_path": "path/to/file",
    "new_line": 123
  }
}
```

После публикации вернуть ссылку на MR, число созданных discussions и их severity; не утверждать, что
они inline, пока это не подтверждено чтением API.
