# SDD Review

Пятый этап SDD-процесса: проверить то, что сделал `sdd-apply`, до того как `sdd-archive` перенесёт дельты в `sdd/specs/`. Проводить анализ внешней моделью другого семейства, чтобы вызывающий агент не ревьюил собственным семейством моделей.

Проверка идёт по двум независимым осям: **Требования** (делает ли код то, что записано в дельтах) и **Стандарты** (написан ли код по правилам проекта). Оси не смешиваются — изменение может пройти одну и провалить другую.

## Конвенция каталога sdd/ (кратко)

```text
sdd/
├── specs/<capability>/spec.md         # актуальные требования — этот скилл только читает
└── changes/<change-id>/
    ├── proposal.md                    # границы изменения
    ├── design.md                      # опционально
    ├── tasks.md                       # все задачи должны быть "- [x]"
    ├── specs/<capability>/spec.md     # дельты требований — критерии приёмки
    └── review.md                      # вердикт — создаёт этот скилл
```

## Когда использовать

После `sdd-apply`, когда все задачи в `tasks.md` отмечены `- [x]`, и перед `sdd-archive`.

## Входное условие

Существует `sdd/changes/<change-id>/` с `proposal.md`, `tasks.md` и дельтами требований. Если в `tasks.md` остались невыполненные задачи — не начинать ревью, а показать список оставшегося: ревьюить незаконченную работу бессмысленно.

Работа идёт в ветке изменения `feature/<change-id>`, отведённой на этапе `sdd-propose`. Если текущая ветка базовая (`main`, `master`, `trunk` или другая ветка по умолчанию) — остановиться и предложить переключиться.

## Шаг 1. Выполнить предварительные проверки

До запуска внешней модели:

1. Найти `sdd/changes/<change-id>/`.
2. Убедиться, что существуют `proposal.md`, `tasks.md` и хотя бы одна дельта `specs/<capability>/spec.md`.
3. Убедиться, что все элементы чеклиста в `tasks.md` отмечены `- [x]`. При наличии незавершённых задач остановиться и перечислить их.
4. Убедиться, что текущая ветка не базовая (`main`, `master`, `trunk` или другая ветка по умолчанию). На базовой ветке остановиться и предложить переключиться.
5. Если пользователь явно назвал baseline, сохранить его для аргумента `--baseline`.

Раннер повторно проверяет эти условия, находит коммит появления `proposal.md`, разрешает baseline и собирает diff без изменения репозитория. Для чистого дерева он использует `git diff <ref>...HEAD`, для грязного — `git diff <ref>` и список неотслеживаемых файлов. Если baseline неизвестен, использует рабочий diff относительно `HEAD`.

Если `sdd/` лежит в отдельном репозитории спецификаций (раздел «Отдельный репозиторий спецификаций» в `spec-format.md` скилла `sdd-propose`), реализация лежит в клонах репозиториев кода. Определить затронутые репозитории по «Влиянию» proposal и группам `tasks.md` и передать каждый раннеру аргументом `--code-repo`. Точка отсчёта клона — `merge-base` его `HEAD` с веткой по умолчанию (`origin/HEAD`); другую задать как `--code-repo <путь>=<ref>`. Раннер проверяет, что ни один репозиторий не стоит на базовой ветке, и передаёт ревьюерам diff каждого.

## Шаг 2. Запустить обязательное кросс-семейное ревью

Определить вызывающий харнесс из системного контекста:

- в Codex передать `--caller codex`; раннер запустит Claude Code CLI;
- в Claude Code передать `--caller claude`; раннер запустит Codex CLI;
- в другой или неоднозначной среде остановиться: автоматического выбора и same-family fallback нет.

Из корня репозитория выполнить:

```bash
python3 <skill-dir>/scripts/run_cross_review.py \
  --caller <codex|claude> \
  --repo "$PWD" \
  --change-id <change-id> \
  --claude-bin vclaude \
  --pretty
```

Для вызывающего Codex по умолчанию использовать `--claude-bin vclaude`, если в окружении
настроена VPN-функция `vclaude`. Runner распознаёт это имя как zsh-функцию и запускает её
через интерактивный zsh; обычный бинарный Claude CLI по-прежнему можно выбрать явно через
`--claude-bin claude` или `SDD_REVIEW_CLAUDE_BIN`.

Если пользователь задал baseline, добавить `--baseline <ref>`. В отдельном репозитории спецификаций запускать из его корня и добавить `--code-repo <клон>` на каждый затронутый репозиторий кода.

При необходимости выбрать модель через `SDD_REVIEW_CODEX_MODEL` или `SDD_REVIEW_CLAUDE_MODEL`. Не придумывать slug модели: если переменная не задана, использовать настроенную по умолчанию модель CLI и записать в отчёт «настройка CLI по умолчанию».

Уровень рассуждений Codex задаётся через `SDD_REVIEW_CODEX_REASONING_EFFORT` или `--codex-reasoning-effort` (например, `high`); раннер передаёт его как `-c model_reasoning_effort=<значение>`. Codex запускается с `--ignore-user-config`, поэтому модель и уровень рассуждений из `~/.codex/config.toml` не применяются: без переменных используется встроенное значение CLI по умолчанию. Если переменная не задана, записать в отчёт «настройка CLI по умолчанию».

Раннер обязан:

- выбрать CLI противоположного семейства;
- отключить дочерние скиллы и slash-команды, выставить `SDD_REVIEW_LEAF=1` и запретить повторную делегацию в промпте;
- запустить оси `requirements` и `standards` параллельно в двух независимых процессах;
- дать дочерним процессам только read-only доступ;
- передать собранный diff, критерии и неотслеживаемые файлы;
- передать оси стандартов полный базовый каталог запахов;
- передать обеим осям шкалу severity;
- если `review.md` уже существует, передать его как результат предыдущего раунда: ревьюер не возвращает отклонённые пользователем находки, повторяет неустранённые с прежней severity и сообщает о новых находках только уровня `medium` и выше;
- потребовать структурированный JSON и проверить его семантику;
- ничего не записывать в репозиторий.

Если противоположный CLI отсутствует, не авторизован, превысил timeout, вернул ошибку или невалидный результат — остановиться. Показать ошибку и способ повторить запуск. Не проводить ревью текущей моделью и не использовать частичный результат одной оси.

## Шаг 3. Проверить результат

Разобрать JSON из stdout раннера. Проверить:

- `reviewer.backend` противоположен `reviewer.caller`;
- присутствуют обе оси: `requirements` и `standards`;
- у каждой находки есть точное место, критерий с цитатой, доказательство и влияние;
- находки требований имеют `classification=violation`;
- нарушения документированных стандартов имеют `classification=violation`;
- запахи имеют `classification=judgment`.

## Шаг 4. Проверить блокирующие находки по коду

Блокирующие находки — находки оси Требования с severity `critical`, `high` или `medium`, не отклонённые пользователем. Находки `low` и все находки оси Стандарты не блокируют.

Каждую блокирующую находку проверить по реальному коду, дельтам и тестам и дать ей оценку:

- `подтверждено` — цитата критерия верна, место указано правильно, доказательство соответствует коду;
- `оспорено` — находка не подтверждается; записать конкретное контрдоказательство (файл, строка, тест).

Не понижать severity и не отклонять находку самостоятельно: оспоренная находка остаётся блокирующей, пока её не отклонит пользователь. Задача шага — не тратить цикл исправлений на ложные срабатывания, а не заменить внешнее ревью мнением вызывающей модели.

## Шаг 5. Отчёт и вердикт

Показать пользователю оба отчёта под заголовками `## Требования` и `## Стандарты`. Не сливать, не переносить и не переупорядочивать находки между осями. Для каждой находки показать severity, место, критерий, доказательство, влияние и предлагаемое направление исправления, для блокирующих — ещё и оценку из шага 4. Если массив пуст, написать «замечаний нет».

Завершить сводкой: количество находок и худшая severity отдельно по каждой оси в порядке `critical > high > medium > low`. Не выбирать «главную проблему» поперёк осей.

Номер раунда: 1, если `review.md` ещё нет, иначе номер из прежнего `review.md` плюс один. Раздел «Решения по находкам» перенести из прежнего `review.md` и дополнить: находку прошлого раунда, по которой в `tasks.md` выполнена задача и которую ревьюер не вернул, записать как исправленную.

Записать результат в `sdd/changes/<change-id>/review.md`:

```markdown
# Ревью <change-id> — <дата>

Раунд: <N>
Точка отсчёта: <baseline или «рабочее дерево относительно HEAD»; в отдельном репозитории спецификаций — по каждому репозиторию: `<репозиторий>: <baseline>`>
Оркестратор: <Codex | Claude Code>
Исполнитель: <backend и cli_version>
Модель: <явный model или «настройка CLI по умолчанию»>
Уровень рассуждений: <явный reasoning effort Codex или «настройка CLI по умолчанию»>

## Требования
<находки или «замечаний нет»; у блокирующих — «подтверждено» или «оспорено: <контрдоказательство>»>

## Стандарты
<находки или «замечаний нет»>

## Решения по находкам
<«<находка> — исправлено в раунде K» или «<находка> — отклонено пользователем в раунде K: <причина>»; если записей нет — «нет»>

## Вердикт
<пройдено | не пройдено — B блокирующих замечаний по требованиям (из них D оспорено); всего замечаний: N по требованиям, M по стандартам>
```

Создать или полностью обновить `review.md` только после успешного получения обеих осей. Вердикт «пройдено» ставится, когда на оси Требования нет блокирующих находок. Находки `low` и замечания по оси Стандарты архивацию не блокируют — они остаются в `review.md` как повод для отдельной работы.

## Шаг 6. Цикл исправлений

Лимит — 3 раунда ревью на изменение: первичное и два повторных.

Если вердикт «не пройдено»:

1. Если есть оспоренные блокирующие находки — показать их пользователю с контрдоказательствами и спросить по каждой: исправлять или отклонить. Отклонённую находку записать в «Решения по находкам» с причиной, названной пользователем, и пересчитать вердикт.
2. Если блокирующие находки остались и номер раунда меньше 3 — без дополнительного подтверждения перейти к `sdd-apply` для исправления замечаний, а после него запустить следующий раунд `sdd-review`.
3. Если номер раунда равен 3 или больше — остановиться. Показать оставшиеся блокирующие находки и предложить варианты: разрешить ещё один раунд, отклонить часть находок, вернуться к `sdd-propose`, если находки вскрыли проблему в требованиях, или продавить архивацию вопреки вердикту. Каждый раунд сверх лимита запускать только по явному разрешению пользователя.

Неблокирующие находки в цикл исправлений не попадают и исправляются только по явной просьбе пользователя.

Пользователь может продавить архивацию вопреки вердикту; тогда его решение записывается в `review.md` отдельной строкой, а не подменяет вердикт.

## Разделение ответственности

`sdd-review` ничего не чинит: он не правит код, не дописывает тесты и не меняет требования. Правки по замечаниям делает `sdd-apply`, требования меняет только `sdd-propose`, `sdd/specs/` меняет только `sdd-archive`. Единственный файл, который создаёт этот скилл, — `review.md`.
