# Acceptance Run

Прогон приёмочных сценариев на живом стенде через браузер. Задача скилла — честно установить, что работает, а что нет, и оставить доказательства. Не починить, не обойти, не «подтвердить общее впечатление».

## Обязательное условие: Playwright MCP

Все действия в браузере выполняются инструментами Playwright MCP, доступными в сессии (навигация, снимок страницы, клик, ввод, скриншот). Если этих инструментов в сессии нет — остановиться и сказать пользователю, что скилл без них неприменим, а не пытаться заменить их чем-то другим.

Чем нельзя подменять браузер: HTTP-запросами (`curl`, `httpie`), обращениями к API или к базе, запуском собственных скриптов на Playwright. Приёмочный тест проверяет то, что видит пользователь в интерфейсе; всё остальное проверяет другое.

Доступность по харнесам: в Codex и Claude Code сервер Playwright подключён глобально. В pi протокола MCP нет вовсе — там приёмочные тесты не прогоняются, это осознанное исключение; сказать об этом пользователю сразу и не искать обходных путей.

## Входные данные

Нужны три вещи, все до начала прогона:

1. **Файл со сценариями** — markdown, где у каждого сценария есть шаги и ожидаемый результат.
2. **Адрес стенда** — базовый URL.
3. **Учётные записи** — логин, пароль и роль для каждой роли, встречающейся в сценариях.

Чего-то не хватает — запросить у пользователя и не начинать. Не подбирать учётки, не угадывать адрес стенда, не додумывать роли.

## Порядок прогона

Сценарии выполняются **строго по одному**, в порядке файла. Не запускать их параллельно: стенд общий, состояние одного сценария влияет на другой.

Для каждого сценария:

1. Привести сессию к нужной роли — выйти из текущей учётной записи или открыть чистый контекст браузера, затем войти под требуемой. Не полагаться на то, что осталось от предыдущего сценария.
2. Выполнить шаги буквально так, как они записаны. Не добавлять шаги, которых в сценарии нет.
3. Сверить ожидаемый результат с тем, что реально видно на странице — по снимку или скриншоту, а не по косвенным признакам вроде «страница не выдала ошибку» или «запрос ушёл».
4. На первом же расхождении сценарий считается проваленным: зафиксировать доказательства и перейти к следующему, не доигрывая оставшиеся шаги.

Если шаг сценария сформулирован неоднозначно и допускает разное поведение — не угадывать. Отметить это в отчёте как дефект самого сценария и указать, какое прочтение было выбрано.

## Подготовка недостающих данных

Часто сценарий требует сущность или состояние, которых на стенде нет. Тогда:

1. Проверить, можно ли создать нужное через интерфейс под одной из выданных ролей. Типичный случай — админ заводит сущность, после чего сценарий проходит под обычным пользователем.
2. Выполнить подготовку **отдельным явным шагом**, который не входит в проверяемый сценарий, и записать в отчёт: что создано, под какой ролью, каким путём в интерфейсе.
3. Если подготовить данные нельзя ни под одной из выданных ролей — сценарий помечается **заблокированным** с указанием, чего именно не хватило.
4. После сценария по возможности удалить созданное. Если удалить нельзя — записать это в отчёт как оставшиеся на стенде данные.

Три статуса различаются строго, смешивать их нельзя:

- **пройден** — ожидаемый результат наблюдался;
- **провален** — ожидаемый результат не наблюдался, продукт ведёт себя иначе;
- **заблокирован** — проверить не удалось: нет данных, нет доступа, стенд недоступен. Это не провал продукта, и выдавать одно за другое нельзя ни в ту, ни в другую сторону.

## Доказательства

Скриншот делается для каждого сценария; для проваленного — обязательно и в момент расхождения, до любых дальнейших действий.

```text
acceptance/<YYYY-MM-DD-HHMM>/
├── report.md
└── <scenario-id>/
    ├── 01-<краткий-шаг>.png
    └── 02-<краткий-шаг>.png
```

Для каждого провала записать: идентификатор и название сценария, шаг, на котором разошлось, **ожидаемое поведение**, **фактическое поведение**, адрес страницы, роль, время и имя файла со скриншотом.

## Отчёт

`report.md` в каталоге прогона содержит:

- шапку — стенд, дата и время прогона, файл сценариев, использованные роли (без паролей);
- таблицу: сценарий, роль, статус, ссылка на доказательства;
- сводку: сколько пройдено, провалено, заблокировано;
- раздел с деталями каждого провала по формату выше;
- раздел с подготовленными данными и тем, что осталось на стенде после прогона.

Отчёт показать пользователю целиком, не пересказывая «в целом всё хорошо».

## Секреты

Пароли не попадают ни в отчёт, ни в имена файлов, ни в скриншоты. Если на кадре видно поле с паролем — такой кадр не сохранять, сделать другой.

## Антипаттерны

- **Никогда** не помечать сценарий пройденным без наблюдаемого подтверждения на странице
- **Никогда** не чинить приложение по ходу прогона и не править файл со сценариями — это прогон, а не разработка
- **Никогда** не подменять проверку интерфейса запросом к API или базе
- **Никогда** не использовать учётные записи, которых не дал пользователь, и не менять пароли тестовых пользователей
- **Не** пропускать сценарии молча — пропуск это статус «заблокирован» с причиной
- **Не** перезапускать упавший сценарий в надежде, что получится: повтор допустим только при явной инфраструктурной ошибке (обрыв сети, таймаут стенда), и факт повтора записывается в отчёт
- **Не** сводить итог к проценту успешных: провалы перечисляются поимённо
