# Формат каталога sdd/ и требований

Это канон файловой конвенции SDD-процесса (Spec-Driven Development). На него ссылаются скиллы
`sdd-design`, `sdd-tasks`, `sdd-apply`, `sdd-archive` — при изменении структуры здесь нужно синхронно
поправить упоминания в них.

## Структура каталога

```text
sdd/
├── specs/<capability>/spec.md          # актуальные требования — источник правды
└── changes/
    ├── <change-id>/                    # активное изменение, kebab-case, напр. add-user-export
    │   ├── proposal.md                 # Зачем / Что меняется / Влияние
    │   ├── design.md                   # опционально — создаёт sdd-design
    │   ├── tasks.md                    # чеклист — создаёт sdd-tasks
    │   └── specs/<capability>/spec.md  # дельты требований
    └── archive/                        # завершённые изменения — переносит sdd-archive
```

`sdd/specs/<capability>/spec.md` меняется только при архивации изменения (`sdd-archive`). Пока
изменение активно, требования живут как дельты в `sdd/changes/<change-id>/specs/`.

## Формат требования

И в `sdd/specs/`, и в дельтах требование оформляется одинаково:

```markdown
### Requirement: <краткое название>
Система ДОЛЖНА <проверяемое утверждение>.

#### Scenario: <название сценария>
- **WHEN** <условие/действие>
- **THEN** <ожидаемый результат>
```

У каждого требования — минимум один `Scenario`. Формулировка требования должна быть проверяемой:
«Система ДОЛЖНА» + конкретное поведение, а не намерение или пожелание.

## Формат дельта-файла

Дельта-файл (`sdd/changes/<change-id>/specs/<capability>/spec.md`) группирует требования под тремя
возможными заголовками:

```markdown
## ADDED Requirements

### Requirement: <название нового требования>
Система ДОЛЖНА ...

#### Scenario: ...
- **WHEN** ...
- **THEN** ...

## MODIFIED Requirements

### Requirement: <название существующего требования>
<полный новый текст требования — не диф, а целиком>

#### Scenario: ...
- **WHEN** ...
- **THEN** ...

## REMOVED Requirements

### Requirement: <название удаляемого требования>
Причина удаления: <почему требование больше не нужно>
```

- `ADDED` — новое требование, которого не было в `sdd/specs/`.
- `MODIFIED` — приводится **полный** новый текст требования целиком, не только изменившаяся часть.
- `REMOVED` — только заголовок требования и причина удаления, без текста самого требования.

Дельта-файл может содержать любую комбинацию из трёх секций — используются только нужные.

## Отдельный репозиторий спецификаций

Продукт из нескольких репозиториев кода (например, бэкенд и фронтенд) может вести требования в
отдельном репозитории спецификаций. Тогда `sdd/` лежит только в нём, а репозитории кода
клонируются внутрь него и в его git не попадают. Иначе сквозная фича оформляется дважды: два
proposal, два `tasks.md` и одна capability в двух спеках, которые приходится согласовывать вручную.

Режим узнаётся по инструкциям репозитория, где лежит `sdd/` (`AGENTS.md`): они называют его
репозиторием спецификаций и перечисляют репозитории кода и способ получить их клоны. Скиллы
запускаются из корня репозитория спецификаций — так агент видит требования и весь код.

- Спека описывает поведение продукта, а не репозитория: одна capability — один `spec.md`, даже
  если её реализуют несколько репозиториев.
- У изменения один `proposal.md`, один `design.md` и один `tasks.md`. «Влияние» proposal называет
  затронутые репозитории кода, задачи в `tasks.md` сгруппированы по ним.
- Ветка изменения с одним именем есть в репозитории спецификаций и в каждом затронутом репозитории
  кода: общее имя связывает MR одного изменения.
- Код меняется, собирается и проверяется в клоне своего репозитория по его инструкциям; артефакты
  SDD пишутся только в репозиторий спецификаций.
- Ссылки из `sdd/` на код — абсолютные URL хостинга: клоны не попадают в git репозитория
  спецификаций, и относительная ссылка на них в веб-интерфейсе не откроется.
- MR открывается в каждом затронутом репозитории. MR репозитория спецификаций ссылается на MR кода
  и сливается последним, чтобы `sdd/specs/` базовой ветки не описывали ещё не влитый код.
