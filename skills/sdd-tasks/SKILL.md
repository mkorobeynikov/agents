# SDD Tasks

Третий этап SDD-процесса: превращает одобренный proposal (и design, если он есть) в чеклист реализации, где каждая задача привязана к конкретному требованию.

## Конвенция каталога sdd/ (кратко)

```text
sdd/
├── specs/<capability>/spec.md          # актуальные требования — источник правды
└── changes/<change-id>/
    ├── proposal.md                     # Зачем / Что меняется / Влияние
    ├── design.md                       # опционально, из sdd-design
    ├── tasks.md                        # создаёт этот скилл
    └── specs/<capability>/spec.md      # дельты требований
```

Полное описание формата требований и дельт — в `spec-format.md` скилла `sdd-propose`.

## Когда использовать

После того как proposal одобрен пользователем (и design.md проработан, если этап `sdd-design` не был пропущен) — перед тем как приступать к реализации. Декомпозиция нужна, чтобы прогресс реализации был виден по чекбоксам, а не только по ощущениям.

## Входное условие

Существует `sdd/changes/<change-id>/proposal.md`, одобренный пользователем; `design.md` — опционально, если этап `sdd-design` был пройден.

Работа идёт в ветке изменения `feature/<change-id>`, отведённой на этапе `sdd-propose`. Если текущая ветка базовая (`main`, `master`, `trunk` или другая ветка по умолчанию) — остановиться и предложить переключиться: этапы SDD в базовую ветку не пишут.

## Алгоритм

1. Прочитать `proposal.md`, `design.md` (если есть) и дельты требований в `sdd/changes/<change-id>/specs/`.
2. Разбить работу на группы и задачи в `sdd/changes/<change-id>/tasks.md` строго в формате:

   ```markdown
   ## 1. <этап>
   - [ ] 1.1 <задача>
   - [ ] 1.2 <задача>

   ## 2. <этап>
   - [ ] 2.1 <задача>
   ```

   Формат строгий: нумерованные группы `## N. <этап>`, задачи — чекбоксы `- [ ] N.M <задача>`. На этот формат опирается `sdd-apply` при выполнении задач по порядку.
3. К каждой задаче привязать требование, которое она реализует: `→ Requirement: <название>`.
4. Включить отдельные задачи на локальные автоматизированные тесты для Scenario, воспроизводимых на уровне репозитория. Scenario остаются критериями приёмки, но `tasks.md` покрывает только локальную реализацию и локальные проверки.
5. Показать пользователю итоговый tasks.md.

## Отдельный репозиторий спецификаций

Если `sdd/` лежит в отдельном репозитории спецификаций (раздел «Отдельный репозиторий спецификаций» в `spec-format.md` скилла `sdd-propose`), задачи группируются по репозиториям кода из «Влияния» proposal. Этапы вложены в репозиторий на уровень ниже, нумерация этапов сквозная по всему файлу — номер задачи однозначен без указания репозитория:

```markdown
## <репозиторий-кода>
### 1. <этап>
- [ ] 1.1 <задача>

## <другой-репозиторий-кода>
### 2. <этап>
- [ ] 2.1 <задача>
```

- Репозитории идут в порядке поставки: первым тот, что отдаёт контракт другим (обычно бэкенд), — задачи потребителя опираются на готовый контракт.
- Задача на тест кладётся в тот репозиторий, где проверяется Scenario.
- Ветка изменения проверяется в репозитории спецификаций: `tasks.md` пишется туда.

Если в текущем репозитории нет `sdd/`, а его инструкции (`AGENTS.md`) указывают на отдельный репозиторий спецификаций, это клон репозитория кода. Остановиться и предложить запустить скилл из корня репозитория спецификаций: `sdd/`, созданный здесь, развёл бы требования по двум местам, а изменения из репозитория спецификаций отсюда не видны.

## Правила размера задач

Порядок задач в списке — это порядок их выполнения. Каждая задача — проверяемый результат объёмом не больше одного дня работы: если задача крупнее, её нужно дробить дальше, иначе прогресс по чеклисту перестаёт отражать реальное состояние работы.

## Разделение ответственности

`sdd-tasks` не меняет требования. Если при декомпозиции обнаружилась дыра в требованиях (задача не может быть проверяемой, потому что требование сформулировано нечётко или чего-то не хватает) — это повод остановиться и вернуться к `sdd-propose` для обновления proposal и дельт, а не подгонять задачи под неполную спеку.

Не добавлять в `tasks.md` задачи на деплой, публикацию, подготовку стенда или проверку поведения на стенде. Такие проверки выполняются только после `sdd-archive` и `ship` и не должны блокировать завершение локального этапа `sdd-apply`.
