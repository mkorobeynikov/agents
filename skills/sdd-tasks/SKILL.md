# SDD Tasks

Третий этап SDD-процесса: превращает одобренный proposal (и design, если он есть) в чеклист реализации, где каждая задача привязана к конкретному требованию.

## Конвенция каталога sdd/ (кратко)

```text
sdd/
├── specs/<capability>/spec.md          # актуальные требования — источник правды
└── changes/<change-id>/
    ├── proposal.md                     # Зачем / Что меняется / Влияние
    ├── design.md                       # опционально, из sdd-design
    ├── tasks.md                        # создаёт этот скилл
    └── specs/<capability>/spec.md      # дельты требований
```

Полное описание формата требований и дельт — в `spec-format.md` скилла `sdd-propose`.

## Когда использовать

После того как proposal одобрен пользователем (и design.md проработан, если этап `sdd-design` не был пропущен) — перед тем как приступать к реализации. Декомпозиция нужна, чтобы прогресс реализации был виден по чекбоксам, а не только по ощущениям.

## Входное условие

Существует `sdd/changes/<change-id>/proposal.md`, одобренный пользователем; `design.md` — опционально, если этап `sdd-design` был пройден.

Работа идёт в ветке изменения `feature/<change-id>`, отведённой на этапе `sdd-propose`. Если текущая ветка базовая (`main`/`master`) — остановиться и предложить переключиться: этапы SDD в базовую ветку не пишут.

## Алгоритм

1. Прочитать `proposal.md`, `design.md` (если есть) и дельты требований в `sdd/changes/<change-id>/specs/`.
2. Разбить работу на группы и задачи в `sdd/changes/<change-id>/tasks.md` строго в формате:

   ```markdown
   ## 1. <этап>
   - [ ] 1.1 <задача>
   - [ ] 1.2 <задача>

   ## 2. <этап>
   - [ ] 2.1 <задача>
   ```

   Формат строгий: нумерованные группы `## N. <этап>`, задачи — чекбоксы `- [ ] N.M <задача>`. На этот формат опирается `sdd-apply` при выполнении задач по порядку.
3. К каждой задаче привязать требование, которое она реализует: `→ Requirement: <название>`.
4. Включить отдельные задачи на тесты по каждому Scenario из дельт требований — Scenario является критерием приёмки, и это должно быть видно в чеклисте, а не подразумеваться.
5. Показать пользователю итоговый tasks.md.

## Правила размера задач

Порядок задач в списке — это порядок их выполнения. Каждая задача — проверяемый результат объёмом не больше одного дня работы: если задача крупнее, её нужно дробить дальше, иначе прогресс по чеклисту перестаёт отражать реальное состояние работы.

## Разделение ответственности

`sdd-tasks` не меняет требования. Если при декомпозиции обнаружилась дыра в требованиях (задача не может быть проверяемой, потому что требование сформулировано нечётко или чего-то не хватает) — это повод остановиться и вернуться к `sdd-propose` для обновления proposal и дельт, а не подгонять задачи под неполную спеку.
