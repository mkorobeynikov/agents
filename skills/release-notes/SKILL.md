# Release notes — из коммитов за день

Собирает пользовательские release notes из git-коммитов за один календарный день
и печатает их строго в принятом формате. Итог — **текст в чат** (никаких файлов и
коммитов), потому что рассылку/публикацию человек делает сам.

## Когда использовать

- «Собери release notes за сегодня / за сутки / за 16 июля».
- «Дай ноутсы из коммитов».

## Шаг 1. Определить день

- По умолчанию — **сегодня** (дата берётся из окружения / `date`).
- Если пользователь назвал дату — берём её.
- Один выпуск = один календарный день. Коммиты прошлых дней в него не входят
  (у них свой выпуск), поэтому окно всегда сутки, а не «последние N коммитов».

## Шаг 2. Собрать коммиты за этот день

```
git log --no-merges \
  --since="<YYYY-MM-DD> 00:00" --until="<YYYY-MM-DD> 23:59:59" \
  --date=format:'%Y-%m-%d %H:%M' \
  --pretty=format:'%h | %ad | %an | %s%n%b%n----'
```

Читаем и заголовок (`%s`), и тело (`%b`) — тело часто объясняет суть/причину.

## Шаг 3. Классифицировать и отобрать

Тип берём из conventional-commit префикса заголовка:

- **✨ Новое** — `feat` (новая функциональность, эндпоинт, компонент, возможность).
- **🛠 Исправления** — `fix` (исправление поведения).
- `chore`/`style`/`test`/`build`/`ci`/`refactor`/`docs` — **по умолчанию не включаем**
  (внутренний шум). Исключение: если у изменения есть реальный эффект для
  пользователя или поведения системы — включаем, но описываем **по эффекту**, а не
  по букве коммита.

Правило про невнятные заголовки: коммит вида «исправлена опечатка», «мелкая правка»
включаем только если реально есть эффект — тогда **посмотри дифф** (`git show <hash>`)
и опиши, что этот эффект даёт (пример: правка имени kind в правилах видимости → «роль
снова видит такой-то артефакт»). Если эффекта нет — пропусти.

## Шаг 4. Написать строки

Формат строки:

```
- **<Заголовок человеческим языком>** — <короткое пояснение сути/пользы> (<Автор>)
```

- Переводи conventional-commit + тело в **пользовательский** язык: что это даёт и
  зачем, а не дословный текст коммита. Технический термин оставляй, только если он
  и есть суть (Mermaid, SSE, MCP, OTAR-дельта).
- Сохраняй ссылки на задачи в скобках, если есть в коммите: `(#86)`.
- Одна строка = одно осмысленное изменение. Несколько коммитов одной темы можно
  слить в одну строку; один коммит с несколькими темами — при необходимости разбить.

## Шаг 5. Авторы

Имя автора — из `%an`, но в **русской** форме. Карта известных авторов:

| git (`%an`)         | В выпуске           |
|---------------------|---------------------|
| Anton Kaplin        | Антон Каплин        |
| Maksim Korobeynikov | Максим Коробейников |
| Константин Потапов  | Константин Потапов  |

Неизвестного автора пиши как в git. Не угадывай пол/род — формулируй нейтрально.

## Шаг 6. Собрать выпуск

Заголовок: `Release notes — <день> <месяц в родительном падеже> <год>`
(январь→января, февраль→февраля, март→марта, апрель→апреля, май→мая, июнь→июня,
июль→июля, август→августа, сентябрь→сентября, октябрь→октября, ноябрь→ноября,
декабрь→декабря).

Порядок: сначала **✨ Новое**, затем **🛠 Исправления**. Внутри секции — сначала
самое продуктовое/видимое пользователю, внутренние изменения ниже. Если в секции
нет пунктов — секцию не печатать.

Шаблон:

```
Release notes — 17 июля 2026

✨ Новое
- **Заголовок** — пояснение (Автор)

🛠 Исправления
- **Заголовок** — пояснение (Автор)
```

## Шаг 7. После вывода

Одной короткой строкой предложи убрать более «внутренние» пункты (ADR, инфра,
рефакторинг агентов), если рассылка идёт на нетехническую аудиторию. Ничего не
коммить и не публиковать — только текст.
