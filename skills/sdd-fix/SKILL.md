# SDD Fix

Облегчённая ветка SDD-процесса для дефектов: чинится код, требования не меняются. Полный цикл (`sdd-propose` → `sdd-design` → `sdd-tasks` → `sdd-apply` → `sdd-archive`) для однократного фикса избыточен, но чинить полностью мимо процесса тоже нельзя — иначе `sdd/specs/` начнёт молча расходиться с кодом.

## Конвенция каталога sdd/ (кратко)

```text
sdd/
├── specs/<capability>/spec.md    # актуальные требования — этот скилл только читает
├── changes/<change-id>/          # полный цикл изменений — этот скилл сюда не пишет
└── fixes/YYYY-MM-DD-<slug>.md    # запись о фиксе — создаёт этот скилл
```

## Триаж — обязательный первый шаг

Найти в `sdd/specs/` требование, покрывающее ожидаемое поведение, и выбрать ветку:

- **Требование есть и оно верное** — код ему не соответствует. Это дефект, чинить по алгоритму ниже.
- **Требования нет либо оно описывает неправильное поведение** — это пробел или ошибка в требованиях. Остановиться и перейти к `sdd-propose`: `ADDED` и `MODIFIED` попадают в спеки только через полный цикл.
- **Наблюдаемое поведение не затронуто** (опечатка в логе, упавшая сборка, форматирование) — чинить напрямую, SDD здесь не нужен, файл в `sdd/fixes/` не создавать.

При сомнении выбирать `sdd-propose`. Лишний proposal стоит только времени, а пропущенное изменение требований оставляет спеку неверной — и по ней потом будут писать следующие изменения.

## Алгоритм

1. Воспроизвести дефект. Если воспроизвести не удаётся — не чинить наугад, а сказать пользователю, чего не хватает для воспроизведения.
2. Провести триаж. Если ветка оказалась не «дефект» — остановиться и сказать пользователю, куда идти дальше, а не чинить всё равно.
3. Написать тест, который падает на текущем коде и воспроизводит дефект. В тесте сослаться на нарушенное требование из `sdd/specs/`.
4. Починить код минимальным изменением, устраняющим причину, а не симптом.
5. Убедиться, что новый тест зелёный, а остальные не сломались.
6. Создать `sdd/fixes/YYYY-MM-DD-<slug>.md` по формату ниже.
7. Показать пользователю причину дефекта, суть правки и то, каким тестом он теперь закрыт.

## Формат записи

Файл создаётся всегда, когда пошли по ветке «дефект». Ровно четыре строки — запись не должна разрастаться в proposal:

```markdown
# <краткое описание дефекта>

- Симптом: <что наблюдалось>
- Причина: <корневая причина в коде>
- Изменено: <файлы или модули>
- Закрыт: <тест, который теперь это проверяет>
```

Slug — kebab-case по симптому (`export-drops-empty-rows`), дата — дата фикса.

## Разделение ответственности

`sdd-fix` не меняет `sdd/specs/` и не создаёт новых требований — ни одной строки. Требования правятся только через `sdd-propose` и попадают в спеки только через `sdd-archive`. Если по ходу починки выяснилось, что нужное поведение нигде не зафиксировано, это уже не фикс, а изменение требований: остановиться и перейти к `sdd-propose`.

`sdd-fix` также не заводит `sdd/changes/<change-id>/` — у фикса нет ни proposal, ни tasks.md, и `sdd-archive` такой каталог обработать не сможет.
