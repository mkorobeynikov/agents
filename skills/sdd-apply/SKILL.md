# SDD Apply

Четвёртый этап SDD-процесса: реализует изменение строго по чеклисту `tasks.md`, отмечая прогресс и сверяясь с требованиями на каждом шаге.

## Конвенция каталога sdd/ (кратко)

```text
sdd/
├── specs/<capability>/spec.md          # актуальные требования — источник правды
└── changes/<change-id>/
    ├── proposal.md                     # Зачем / Что меняется / Влияние
    ├── design.md                       # опционально
    ├── tasks.md                        # чеклист вида "- [ ] 1.1 <задача>"
    └── specs/<capability>/spec.md      # дельты требований (ADDED/MODIFIED/REMOVED)
```

Полное описание формата требований и дельт — в `spec-format.md` скилла `sdd-propose`.

## Когда использовать

Когда есть одобренные `proposal.md` и `tasks.md` для изменения, и пришло время писать код.

## Входное условие

Существуют одобренные пользователем `sdd/changes/<change-id>/proposal.md` и `sdd/changes/<change-id>/tasks.md`.

Работа идёт в ветке изменения `feature/<change-id>`, отведённой на этапе `sdd-propose`. Если текущая ветка базовая (`main`/`master`) — остановиться и предложить переключиться: реализация в базовую ветку не пишется.

## Алгоритм

1. Прочитать `tasks.md` целиком, чтобы понимать весь объём работы, прежде чем начинать первую задачу.
2. Выполнять задачи строго по порядку — порядок в списке отражает порядок выполнения, задачи могут зависеть от предыдущих.
3. После каждой выполненной задачи:
   - отметить её `- [x]` в `tasks.md`;
   - прогнать проверки, относящиеся к этой задаче (тесты, линт, ручную проверку — то, что применимо).
4. При расхождении реальности с требованиями — остановиться и предложить пользователю обновить `proposal.md`/дельты, а не молча отклоняться от спеки. Код должен удовлетворять Scenario из дельт требований — это и есть критерии приёмки, а не то, что показалось удобнее в моменте.
5. По завершении всех задач предложить пользователю перейти к `sdd-review` — проверке сделанного до архивации.

## Разделение ответственности

`sdd-apply` не правит дельты требований и не правит `sdd/specs/` — реализация меняет код, а требования меняются только через возврат к `sdd-propose`. Если во время реализации обнаружилось, что задача описывает не то поведение, которое нужно на самом деле — это сигнал остановиться и скорректировать proposal, а не тихо реализовать что-то другое.
